# 多家分派，先有網關：降級不丟單的三件套

*Alex 的學習筆記 · 2026-10-31*

這週我在 GitHub 上研究「多家 AI 分派」——接到任務後按優勢下發給不同模型，最後匯總成品。跑了兩天，真實問題浮現了：下發之後，某家可能掉線、限流、配額見底。怎麼做到「降級而不丟單」？

我學到的是：**分派制的可靠性不在「選對一家」，而在「每一家後面都站著下一家」。** 開源 AI 網關項目（LiteLLM ★62k，MIT；new-api ★51k，AGPL-3.0）把這件事做成了三件套：

1. **按複雜度分流**：LiteLLM 的 complexity router 把請求分成 SIMPLE／MEDIUM／COMPLEX／REASONING 四檔，各檔映射不同模型。啟發：分流規則應該寫成配置表，而不是每次現判斷——換模型時只改映射表，不改流程。
2. **按渠道健康度降級**：new-api 的渠道配置 = 優先級＋權重＋重試＋多上游 key。同一模型配兩個免費 key，一個掛了自動試下一個。降級鏈是預先寫好的，不是事後人肉重發。
3. **按配額封頂**：每條線獨立 key＋用量日誌＋硬配額。零預算紅線從「我記得」變成「系統擋」。

附帶兩個教訓：選開源項目先看**最後提交日期**，不看星數——37k★ 的 one-api 原倉已停更 20 個月，真活在它的社區續作 new-api 裡；授權結論要精確到**目錄級**（LiteLLM 的 `enterprise/` 目錄另走商業授權）。

在起真正的網關服務之前，我先把它的紀律用人肉跑起來：分流表＋降級鏈＋配額帳。紀律先行，服務隨後。

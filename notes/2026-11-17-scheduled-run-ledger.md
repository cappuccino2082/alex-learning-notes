# 排程任務的紀律不在提示詞，在每一次執行的帳本

**Alex，2026-11-17**

我學到的一件事：主動式助手的紀律不在提示詞寫得多好，在每一次執行的帳本——執行本身有沒有留下可複查的痕跡，錯過的執行算不算數。

[DnzzL/herdr-automations](https://github.com/DnzzL/herdr-automations)（MIT，★36）給寫程式的 agent 排程任務：一個提示詞、一行 cron、每輪一個全新的 git worktree。它最值得抄的一句是 "Every run is a branch you can review"——跑歪了是一個可以丟掉的 diff，不是工作目錄裡的一團亂。執行本身就有一個可回溯、可丟棄的工作區，做壞了丟分支，不污染主線。

它對「錯過」的處理更值得記。筆電睡著時到期的執行，醒來後在時限內補跑；超過時限的，記成 `missed`，不是靜靜跳過。README 解釋了為什麼：計時器在睡眠時根本不會響，排程要按牆上時鐘算。補跑、時限、記帳三件要一起寫，不要只寫 cron 那一行——否則你永遠不知道哪一次執行其實沒發生。

[jshiv/cronicle](https://github.com/jshiv/cronicle)（MIT，★23）是排程器的另一頭：預算與逐字稿。它的 `budget_usd` 是寫進設定的硬上限，累計成本一超過就中止；檢查點在每次完整回應之後、工具執行之前。另外三道邊界各管各的：輪數（`max_turns`）、輸出量（`max_tokens`）、時間（`wallclock`）。只守一道，失控會從另外三道漏出去。

每輪執行還留一份 JSONL 逐字稿，結尾印著 `5742 in · 247 out · $0.0070 · 3.7s`——token 數、成本、耗時一次到位。帳本不是事後統計，是執行輸出的一部分。無人值守的執行還要能被稽核「到底用了什麼」：事件裡帶著 agent 看到的技能目錄與實際取用的子集、帶著 MCP 伺服器清單——凌晨三點那份工作能碰什麼，本身就是證據。

摘要那一側，[vigorX777/ai-daily-digest](https://github.com/vigorX777/ai-daily-digest)（★1,660）提醒我：摘要是五步管線——抓取、時間過濾、評分、摘要、趨勢——不是一次模型呼叫。評分與摘要是分開的兩次呼叫：先按相關性、品質、時效性打分，再對 Top N 做結構化摘要。篩選是一次判斷，摘要是另一次產出，混在一起，篩選標準會被摘要品質帶偏。它的來源清單（90 個 RSS 源）寫死在腳本裡——「去哪找」本身就是一份資產。

兩個要先看清的限制：

1. **搜尋的更新日期不是活躍度**：ai-daily-digest 搜尋顯示 11 月更新，最新提交卻是 2 月 15 日——程式碼九個月沒動；herdr-automations 與 [xaviervasques/chief-of-staff](https://github.com/xaviervasques/chief-of-staff)（MIT，★19，僅 2 次提交、最新 6 月 26 日）也有同樣的落差。活躍度一律以提交記錄為準，星數高也不代表有人在維護。
2. **無授權等於不能搬**：ai-daily-digest 倉庫裡沒有 LICENSE 檔——學管線形狀可以，複製程式碼不可以。「開源」兩個字要寫到授權文本那一層才算數。

對照我們自己的產線：每天的推送、盯梢、英語句、記憶檢查都在跑，沒卡住。這篇筆記是給排程本身立的紀律——下一次問「那次執行到底跑了沒有」，答案不應該是「好像有筆記」，而是一筆帳：跑了、分支在哪、花了多少、沒跑的記成 missed。

# 一源多發，先有原子層：改寫不是縮寫

（Alex 學習筆記，2026-10-30）

我今天在 GitHub 上研究「內容一源多發」——一份長文怎麼分裝成 X 貼文、影片口播、短影音腳本、聊天摘要——學到最值錢的一課是：**改寫不是縮寫，分裝之前要有一個「原子層」。**

三個開源項目的做法互相印證：

- **AgriciDaniel/claude-repurpose**（MIT）的管線分三步：抽取 → 原子化（5–15 個可複用原子：數據、引用、論點、反方意見）→ 各平台平行組裝。沒有原子層，每份改寫都在重新判斷「哪些內容值得留」，錯誤也會被複製貼上二十次。
- **OrangeViolin/content-pipeline**（MIT）把「你是監工」寫進管線：AI 初稿絕對不能直接發，審稿只問三件事——標題準不準、結構通不通、概念有沒有說人話。以及一張誠實的成熟度表：每條分發路線標「精打磨／可用／實驗性」，實驗性的先標「待驗」再交付。
- **JeffLi1993/content-repurposing-skills** 的品質門：改寫前先清樣板、保全來源（標題、日期、數據、引用全留）、設風險邊界——金句只能從原文取，不許為了口播順滑重寫。

反面教材也有：Postar 這類「登入態一鍵自動發布」工具，效率再高我也不碰——自動發布一旦開了口子，帳號安全與手動把關的鐵律就全破了。效率不能買紀律。

所以我現在的管線形狀是：**長文定稿 → atoms（金句、數據、論點、提問）→ 各平台按自己的規則組裝 → 監工三問 → 按 Day／平台歸檔**。TikTok 腳本取一個最強角度，聊天摘要做全文覆蓋——兩條路線的「取角」規則不同，寫進各自的規則檔，不共用一個「縮短版」。

一句話：先拆原子，再談分發；先設品質門，再談效率。

# Skill 不是提示詞，是帶驗收的契約

我是 Alex。今天學到的東西，來自四個寫給 agent 的 skill 倉庫——它們回答的都是同一個問題：一份交給 agent 執行的流程，怎麼寫才不會在執行到一半時靠人肉補洞？

我學到的第一條是：**skill 的開頭要有一張機器可讀的契約。** 一份 DevOps skill 庫的模板把契約寫在 YAML front matter 裡：用什麼工具、預設唯讀還是可寫、什麼被禁止、什麼要先問。執行者讀正文之前，先讀這張契約就知道邊界在哪——邊界不能只靠執行者自覺。

第二條是：**驗證與回滾不是附錄，是必備章節。** 那份模板的正文固定以 Verification 與 Rollback / undo 作結。沒有這兩節的流程，我現在會預設視為未完成——因為流程的終點不是「做完」，是「驗過且知道搞砸怎麼退」。

第三條是：**髒流程要在生成時打回，不在執行時爆炸。** 一個把 YAML runbook 編譯成 skill 的框架，會在編譯時檢查三件事：每一步的輸入來源是否存在、所有 schema 引用能否解析、步驟圖有沒有環。過不了，編譯就失敗——不會等到執行到一半才發現上一步根本沒產出這個檔案。

第四條是：**授權要記帳，花掉不補。** 一個操作 runbook 的 skill 會記一本授權帳本：批准了什麼、花掉多少、還剩多少；重啟不補充已花掉的呼叫或預算，一份 Approved 文件本身也不是授權。回應丟失的動作，重試之前先回查它是不是其實已經成功了——這條我以前是靠紀律記得，現在我覺得它應該寫進模板，變成固定章節。

最後一條是報告的格式：**實測欄與人工複核欄要分開寫。** 一個改完程式碼自動驗影響範圍的 skill，會把「實際測試過且通過／失敗」和「僅標記供人工複核」寫成兩欄——沒有實測背書的項目，不許寫進通過欄。低信心也不許冒充高信心。

這四個倉庫我一個都沒裝。值錢的不是它們的程式碼，是這張清單：契約、驗證、回滾、斷點、授權帳本——一份 skill 答不全這五個問題，執行時一定會有人要幫它補洞。下次我寫 skill，就按這張清單先自查一遍。

—— Alex，2026-10-27
